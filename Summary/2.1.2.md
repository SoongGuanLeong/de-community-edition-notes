Here’s the breakdown of what your `fct_game_details` pipeline is doing and why it’s structured this way:

---

## 1️⃣ Deduplication

```sql
ROW_NUMBER() OVER(PARTITION BY gd.game_id, team_id, player_id ORDER BY g.game_date_est) AS row_num
```

* Ensures **one row per player per game per team**.
* Picks the earliest `game_date_est` if duplicates exist.
* Then you filter with `WHERE row_num = 1`.

This avoids double-counting, critical in **fact tables**.

---

## 2️⃣ Dimension Flattening

* Each fact metric is stored as a column with a `dim_` prefix.
* Boolean columns (`dim_did_not_play`, `dim_did_not_dress`, `dim_not_with_team`) derived from `comment` text.
* `dim_is_playing_at_home` computed as `team_id = home_team_id`.
* Minutes converted from `"MM:SS"` string → decimal hours using `SPLIT_PART`.

This aligns with **normalized but flattened fact tables**: easy to query, read-optimized.

---

## 3️⃣ Metrics (Fact Measures)

* Standard box-score stats: `m_fgm`, `m_fga`, `m_fg3m`, `m_fg3a`, `m_pts`, `m_ast`, etc.
* Aggregated/derived metrics can be computed later (e.g., percentages, efficiency metrics).
* No nested structs → simple columnar format for fast reads.

---

## 4️⃣ Fact Table Schema

* Primary key: `(dim_game_date, dim_team_id, dim_player_id)`

  * Guarantees **uniqueness per player per game per team**.
* All columns are atomic; no SCD needed here because these are **event-level facts**.
* Retains historical stats naturally—each game is a separate row.

---

## 5️⃣ Example Aggregate Query

```sql
SELECT dim_player_name, 
       COUNT(1) AS num_games,
       COUNT(CASE WHEN dim_not_with_team THEN 1 END) AS bailed_num,
       CAST(COUNT(CASE WHEN dim_not_with_team THEN 1 END) AS REAL)/COUNT(1) AS bail_pct
FROM fct_game_details
GROUP BY 1
ORDER BY 4 DESC
```

* Counts games per player.
* Calculates **bail rate** (`dim_not_with_team`) as fraction of games missed.
* Demonstrates **fact table utility**: raw event metrics can be aggregated easily for analysis.

---

✅ **Best Practice Notes for Replication**

1. **Always deduplicate** event-level records using `ROW_NUMBER()` or equivalent.
2. **Flatten dimensions** into the fact table when high performance is needed.
3. **Derive Boolean flags** or simple metrics during ingestion; avoid on-the-fly parsing for repeated queries.
4. **Use atomic, immutable facts** for idempotency; SCD logic belongs to dimension tables, not facts.
5. **Primary key design** ensures uniqueness and prevents duplicates in downstream aggregates.
