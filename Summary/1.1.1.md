# 🧠 Core Architectural Principles

## 1️⃣ Snapshot-Based SCD Table

Instead of updating rows in place, you create:

```
PRIMARY KEY (player_name, current_season)
```

This means:

* Each season = new snapshot row
* Table is time-versioned
* You preserve history
* No destructive updates

👉 This maps directly to Iceberg snapshot tables.

---

## 2️⃣ State Stored Inside the Record (Array of Struct)

This is huge.

Instead of:

```
player_seasons (many rows per player)
```

You store:

```
season_stats season_stats[]
```

So each player row contains their full history.

Why this matters:

* Eliminates expensive joins later
* Reduces shuffling
* Makes derived metrics cheap
* Pushes aggregation upstream

This is “pre-aggregation modeling”.

In Spark terms:

* Avoids wide transformations
* Minimizes repartition
* Reduces shuffle stages

---

## 3️⃣ Incremental Upsert Pattern

This pattern:

```
WITH yesterday AS (...)
WITH today AS (...)
FULL OUTER JOIN
```

Is basically:

```
old_state + new_state → new_snapshot
```

This is classic stateful processing.

In Spark/Iceberg this becomes:

```
MERGE INTO target
USING source
```

or

```
streaming upsert with watermark
```

---

## 4️⃣ Derived Columns Computed at Write Time

These fields:

* scoring_class
* years_since_last_season
* current_season

Are computed at ingestion time.

This is important.

Instead of computing downstream every time, you materialize derived business logic early.

That is:

* Faster reads
* BI-friendly tables
* Analytics optimized

---

## 5️⃣ Data Validation via ENUM

```
CREATE TYPE scoring_class AS ENUM(...)
```

This enforces domain constraints.

In Iceberg world, this becomes:

* CHECK constraints
* Or strict schema enforcement
* Or controlled dimension tables

---

## 6️⃣ No Destructive Update

Notice:

* No UPDATE
* No DELETE
* Only INSERT new snapshot

This is append-only modeling.

Perfect for:

* Iceberg
* Delta
* Lakehouse

# 🏗 Patterns We Must Adopt For Your Project

From this file, we extract these standards:

---

### 1. Snapshot Modeling > Overwrite Modeling

Always use:

```
entity_id + version_column
```

Never overwrite current row.

---

### 2. Push State Upstream

Aggregate early.
Store history in nested structs.
Avoid recomputation later.

---

### 3. Materialize Business Logic

Derived features must be written into Silver layer.

Never compute classification in BI dashboard.

---

### 4. Full Outer Join = Stateful Merge

In Spark:

```
MERGE INTO
```

Or:

```
groupByKey + mapGroupsWithState
```

For streaming.

---

### 5. Schema Discipline

Strict schema evolution.
No loose typing.
No dynamic fields.

---
