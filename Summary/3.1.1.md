## 1️⃣ Spark Basics

* **Distributed compute engine**: processes big data efficiently across nodes.
* **Lazy evaluation**: transformations only run when an action (e.g., `collect()`, `write()`) is called.
* **Storage agnostic**: decouples compute from storage (e.g., S3, HDFS, Iceberg).

---

## 2️⃣ Spark Architecture

| Component     | Role                                                                                  |
| ------------- | ------------------------------------------------------------------------------------- |
| **Driver**    | Reads the plan, coordinates executors, decides JOIN strategies, parallelism, laziness |
| **Executors** | Run tasks, perform transformations, store shuffle data                                |
| **Plan**      | Transformation code (SQL, PySpark, Scala)                                             |

**Driver settings**:

* `spark.driver.memory` → heap memory
* `spark.driver.memoryOverheadFactor` → non-heap memory (~10%)

**Executor settings**:

* `spark.executor.memory` → test until no OOM (2–16GB)
* `spark.executor.cores` → 4–6
* `spark.executor.memoryOverheadFactor` → increase for heavy UDF

---

## 3️⃣ JOIN Types

| Type                    | When to Use                                 | Shuffle Required |
| ----------------------- | ------------------------------------------- | ---------------- |
| Shuffle Sort-Merge Join | Default, versatile, works for large tables  | Yes              |
| Broadcast Hash Join     | When one side is small (<10MB default)      | No               |
| Bucket Join             | Both sides pre-bucketed, power-of-2 buckets | No               |

✅ **Tip**: Use broadcast for small tables to avoid shuffles, and bucket tables for repetitive joins.

---

## 4️⃣ Shuffles

* **Enemy of parallelism** → slow, especially >10TB.
* Minimize by:

  * Pre-aggregating data before shuffle
  * Bucketing large tables for repeated joins
  * Using arrays/structs to store multiple values (like metrics arrays)

---

## 5️⃣ Skew

* Happens when partitions have uneven data.
* Detection: jobs hang at 99% completion.
* Fixes:

  * Adaptive Query Execution (Spark 3+): `spark.sql.adaptive.enabled = True`
  * Salting keys to spread heavy keys across partitions
  * Filter or split outliers into separate jobs

---

## 6️⃣ Partitioning & Parallelism

* `spark.sql.shuffle.partitions` → controls shuffle output partitions
* Use powers of 2 for bucketed tables to maximize parallelism.

---

## 7️⃣ Databricks vs Vanilla Spark

| Feature           | Databricks     | Unmanaged Spark    |
| ----------------- | -------------- | ------------------ |
| Notebook workflow | YES            | Only for PoCs      |
| Job testing       | Notebook run   | `spark-submit` CLI |
| Version control   | Git / notebook | Git                |

---

## 8️⃣ Best Practices

1. Partition outputs by date for easier query pruning.
2. Avoid REST API reads in transformations (driver-bound).
3. Use `explain()` on DataFrames to inspect plans.
4. Reduce shuffle by pre-aggregating or using nested structures.
5. Track SCDs and array metrics efficiently for batch/micro-batch pipelines.
