Here’s a concise summary of your **Fact Data Modeling notes** with the key points to replicate in a project:

---

## 1️⃣ What a Fact Table Represents

* Captures **events that happened** (atomic vs aggregated).
* Usually **10–100x larger than dimensions**.
* Can be normalized (write-optimized, store IDs) or denormalized (read-optimized, store aggregated context).
* Derived from raw logs → fact table (cleaned, quality-controlled, meaningful column names).

---

## 2️⃣ Fact Table Pattern: 4Ws + H

* **Who** → IDs (user, player, customer…)
* **Where** → location info, usually via ID
* **How** → method/mode, via ID
* **What** → nature of the event (NOT NULL)
* **When** → timestamp (NOT NULL)
* **Why** → often left out (optional/analytical only)

**Tip**: Fact tables usually store IDs of dimensions; joins can denormalize for performance.

---

## 3️⃣ Raw Logs vs Fact Table

| Raw Logs                         | Fact Table                         |
| -------------------------------- | ---------------------------------- |
| Highly granular, messy schema    | Cleaned, meaningful schema         |
| Many duplicates & quality issues | Deduplicated, quality-checked      |
| Short retention                  | Longer retention (depends on size) |

---

## 4️⃣ Fact Table Design Considerations

* **Denormalization tradeoff**: store IDs only or join dimensions into fact table.
* **Logging discipline**: log only what’s needed for fact table, follow tests/specs.
* **Retention**: balance cost vs utility. Large tables → shorter retention.

---

## 5️⃣ Common Techniques

### Sampling

* Good for approximate analysis, not for critical/secure cases.

### Bucketing / Partitioning

* Pre-partition on key dimensions.
* Helps avoid full table shuffles in joins.
* Use **Sorted-Merge Bucket (SMB) joins** when possible.

### Broadcast Join

* Efficient when one side is small.

### Deduplication

* Essential if events can repeat.
* For large tables, do **micro-batch deduplication**:

  1. Aggregate per hour (`SUM`/`COUNT`, `COLLECT_LIST` for metadata differences).
  2. Full outer join across hours, merge duplicates (strings → `CONCAT`, integers → sum).
* Streaming approach: 15 min–hourly micro-batches depending on memory/data size.

---

✅ **Takeaway for pipeline replication**

1. Maintain a clean, atomic event table.
2. Only store what’s needed; join dimensions later if necessary.
3. Deduplicate and partition intelligently.
4. Retention depends on table size; micro-batch or streaming for duplicates.
5. Fact tables are naturally larger, so consider bucketing/SMB joins for scalability.
