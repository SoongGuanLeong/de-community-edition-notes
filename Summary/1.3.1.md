# 1️⃣ Additive Dimension

## What It Really Means

Additive = no overlapping state for same entity at same time.

Formally:

```text
For a given natural_key and timestamp:
There must be exactly ONE valid record.
```

If not → double counting.

---

## Example Problem

If a user has:

| user_id | status | start | end  |
| ------- | ------ | ----- | ---- |
| 1       | gold   | 2022  | 2023 |
| 1       | silver | 2022  | 2023 |

Then:

```sql
COUNT(user_id)
```

returns 2.

That breaks additivity.

---

## Why It Matters

If dimension is additive:

* `COUNT(*)` works
* `SUM()` works
* no `COUNT(DISTINCT)` needed
* joins remain simple
* queries scale

If not additive:

* every query becomes defensive
* performance degrades
* business logic leaks into BI

---

## Enforce Additivity in Spark

You must validate:

```python
from pyspark.sql.window import Window
from pyspark.sql.functions import count

w = Window.partitionBy("user_id", "date")

df.withColumn("cnt", count("*").over(w)) \
  .filter("cnt > 1")
```

This should return zero rows.

If not → modeling bug.

# 2️⃣ ENUM (Strong Typing for Data)

This is schema enforcement.

Instead of:

```text
status = "gold", "Gold", "GOLD", "gld"
```

You enforce:

```text
status ∈ {gold, silver, bronze}
```

---

## Why ENUM Is Powerful

1. Built-in data validation
2. Prevent silent drift
3. Shared contract across pipelines
4. Enables partitioning/subpartitioning

In Spark + Iceberg:

You simulate ENUM using:

* CHECK constraints
* reference dimension table
* schema validation logic

Professional approach:

Have a small dimension table:

```text
dim_status
```

And join/validate against it.

Never rely on free text.

---

# 3️⃣ Flexible Schema (MAP / JSON Column)

Example:

```text
other_properties MAP<STRING, STRING>
```

---

## When It Is Acceptable

* Event ingestion (Bronze)
* Semi-structured telemetry
* High-cardinality optional fields

---

## When It Is Not Acceptable

* Core analytical dimensions
* Fields used in joins
* Metrics used in aggregations

---

## Engineering Tradeoff

### Pros

* Schema evolution easy
* Fewer ALTER TABLE ops
* Handles messy sources

### Cons

* Worse compression
* Slower filtering
* No predicate pushdown on nested values
* Harder to index
* Harder to test

---

## Professional Rule

Flexible schema allowed only in Bronze.

By Silver:

* flatten
* type cast
* validate
* normalize

Gold must be strongly typed.

---

# 4️⃣ Graph Data Model

This is relationship-centric modeling.

Instead of:

```text
Customer → Order → Product
```

You store:

```text
(subject, object, edge_type)
```

---

## Table Structure

| Column       | Meaning      |
| ------------ | ------------ |
| subject_id   | source node  |
| subject_type | node type    |
| object_id    | target node  |
| object_type  | node type    |
| edge_type    | relationship |
| properties   | attributes   |

---

## Why Graph Is Different

Relational model:

* Entity focused
* Tables represent things

Graph model:

* Relationship focused
* Edges are first-class citizens

---

## When To Use Graph Model

* Many-to-many relationships
* Recursive traversal
* Network analysis
* Recommendations
* Fraud detection

---

## When NOT To Use It

* Simple star schema analytics
* Standard BI dashboards
* Aggregation-heavy workloads

Graph joins are expensive in Spark.

Use only if traversal matters.

# 5️⃣ How All These Concepts Connect

These are all about:

Data integrity + deterministic aggregation.

| Concept       | Protects Against       |
| ------------- | ---------------------- |
| Additivity    | Double counting        |
| ENUM          | Silent drift           |
| SCD2          | Historical instability |
| Idempotency   | Inconsistent rebuild   |
| Strong schema | Downstream chaos       |
| Graph model   | Relationship explosion |

---

# 6️⃣ What This Means for Your Project

For your Spark Lakehouse:

* Dimensions must be additive
* Use SCD2 for changing dims
* ENUM via reference tables
* Flexible schema only in Bronze
* Avoid graph model unless solving network problem
* Validate invariants in tests

---

# Final Engineering Principle

Every dimension must guarantee:

```text
One entity
One state
One interval
One valid record at a time
```

If that invariant holds:

Your analytics will scale cleanly.

If not:

You will constantly patch dashboards.
