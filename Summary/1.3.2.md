## 1️⃣ Vertex Table (`vertices`)

* **Purpose**: Stores entities/nodes in the graph (players, teams, games).
* **Schema**:

| Column     | Type              | Notes                                  |
| ---------- | ----------------- | -------------------------------------- |
| identifier | TEXT              | Unique ID for node                     |
| type       | ENUM              | Node type (`player`, `team`, `game`)   |
| properties | JSON              | Arbitrary properties about the node    |
| PK         | (identifier,type) | Ensures no duplicate node of same type |

* **Implementation Notes**:

  * Each entity type has a JSON payload with relevant metrics or attributes.
  * Deduplication is done using `ROW_NUMBER()` before inserting to avoid duplicates.
  * Aggregation of stats happens for derived metrics (total points, number of games, etc.).

---

## 2️⃣ Edge Table (`edges`)

* **Purpose**: Stores relationships between vertices (edges in the graph).

| Column             | Type      | Notes                                                                   |
| ------------------ | --------- | ----------------------------------------------------------------------- |
| subject_identifier | TEXT      | Source node ID                                                          |
| subject_type       | ENUM      | Node type of source                                                     |
| object_identifier  | TEXT      | Target node ID                                                          |
| object_type        | ENUM      | Node type of target                                                     |
| edge_type          | ENUM      | Type of relationship (`plays_in`, `shares_team`, `plays_against`, etc.) |
| properties         | JSON      | Relationship attributes (points, games played)                          |
| PK                 | Composite | All columns to ensure uniqueness of an edge                             |

* **Implementation Notes**:

  * Deduplicate first to prevent duplicate edges per game.
  * `plays_in` links player → game.
  * `shares_team` or `plays_against` links player → player.
  * Aggregations on edges summarize metrics over multiple games.

---

## 3️⃣ Key Patterns / Engineering Practices

1. **Strong Typing with ENUMs**

   * Enforces valid node/edge types.
   * Prevents invalid relationships in downstream processing.

2. **Properties as JSON**

   * Flexible schema for extra metrics (bronze layer pattern).
   * Can store nested attributes without changing schema constantly.

3. **Deduplication Before Insert**

   * Uses `ROW_NUMBER()` for edges/vertices.
   * Ensures idempotency in inserts.

4. **Aggregation for Analytics**

   * Precompute metrics like total points, number of games.
   * Reduces computation on the query side.

5. **Composite Primary Keys**

   * Prevents accidental duplicates.
   * Supports multi-attribute uniqueness (like edges between two players).

6. **Graph Relationships**

   * Captures many-to-many and recursive relationships naturally.
   * Separate table for vertices vs edges keeps data normalized and queryable.

## 4️⃣ How to Apply in Your Spark + Iceberg Lakehouse

* **Vertices** → Bronze tables with flexible schema (JSON column for properties).

* **ENUM enforcement** → Could be small reference tables and validated in Spark.
* **Aggregation** → Precompute commonly needed metrics in Silver layer to reduce query-time computation.
