Never expose nested Silver directly to BI.

# 3️⃣ Cumulative Table Design = Stateful Snapshot Pattern

This diagram:

```
Yesterday + Today → FULL OUTER JOIN → New Snapshot
```

Is the exact same pattern from the previous SQL file.

State is built incrementally.

Not recomputed from scratch.

# 5️⃣ Struct vs Array vs Map (Design Decision Rules)

Use:

Struct → When schema is fixed
Array → Ordered temporal data
Map → Semi-structured / dynamic keys

In your player example:

season_stats → Array of Struct

Perfect design.

For ecommerce:

order_history → Array of Struct
payment_events → Array of Struct
status_changes → Array of Struct

# 6️⃣ Cardinality Explosion (This Is Advanced)

This is a performance insight most engineers miss.

Problem:

* Temporal dimension causes huge row growth
* Spark shuffles break sorting
* Parquet compression degrades
* Storage explodes

Because:

Parquet uses Run-Length Encoding (RLE)

If sorted:

```
customer_id
1
1
1
1
2
2
2
```

Compresses well.

If shuffled:

```
1
2
1
2
1
2
```

Compression destroyed.

---

# 7️⃣ Two Solutions (Very Important)

Option 1:
Force downstream sorting.

Bad.
Not scalable.
Depends on discipline.

Option 2:
Model nested.

Instead of:

| customer | season | metric |
| -------- | ------ | ------ |

Store:

| customer | season_array |

This:

* Reduces row count
* Improves compression
* Reduces shuffle
* Improves scan speed

That is why nested modeling is powerful.
