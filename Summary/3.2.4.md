## 1️⃣ Bucketed Tables

```scala
CREATE TABLE bootcamp.matches_bucketed (
    match_id STRING,
    is_team_game BOOLEAN,
    playlist_id STRING,
    completion_date TIMESTAMP
)
USING iceberg
PARTITIONED BY (completion_date, bucket(16, match_id));
```

* **Partitioning**: `completion_date` ensures each day’s data is physically stored separately, reducing scan volume.

* **Bucketing**: `bucket(16, match_id)` pre-shuffles the table into 16 consistent buckets by `match_id`.
  ✅ This **reduces shuffle** for joins on `match_id` because rows with the same key end up in the same bucket.

* Same concept applies to `match_details_bucketed`.

---

## 2️⃣ Why `spark.sql.autoBroadcastJoinThreshold` is disabled

```scala
spark.conf.set("spark.sql.autoBroadcastJoinThreshold", "-1")
```

* Spark will **never auto-broadcast** a table.
* Necessary for **big tables** (like matches & match_details) to avoid driver memory OOM.
* Alternative: you can explicitly broadcast **small dimension tables**:

```scala
join(broadcast(matchDetails), $"m.match_id" === $"md.match_id")
```

* Rule of thumb:

  * Big fact table: **do not broadcast**
  * Small reference/dimension table: **broadcast** to save shuffle

---

## 3️⃣ Explaining Joins

```scala
spark.sql("""
    SELECT * FROM bootcamp.match_details_bucketed mdb
    JOIN bootcamp.matches_bucketed md 
    ON mdb.match_id = md.match_id
    AND md.completion_date = DATE('2016-01-01')
""").explain()
```

* Since both tables are bucketed **on `match_id`**, Spark can perform a **bucketed join**:

  * No shuffle required if buckets match.
* Adding a **filter on `completion_date`** further reduces the data scanned for the join.
* In contrast, joining the **raw CSV temp views** (`match_details` × `matches`) triggers a **full shuffle join**, which is slower and memory-intensive.

---

## 4️⃣ Explicit Broadcast vs Threshold

* Explicit broadcast is safer for large clusters:

```scala
matches.as("m")
    .join(broadcast(matchDetails).as("md"), $"m.match_id" === $"md.match_id")
```

* Works best when one table is small (<1–2 GB).

* **Auto threshold** can fail unpredictably if table grows; better to control explicitly.

---

## 5️⃣ Using `.explain()` to Diagnose

* Always check the **physical plan**:

  * Look for `Exchange` → shuffle happening
  * Look for `BroadcastHashJoin` → no shuffle
  * Look for `BucketedHashJoin` → optimal join if tables are bucketed properly

---

## 6️⃣ Practical Tips / Best Practices

1. **Bucket big fact tables** on join key when joins happen often.
2. **Filter early** to reduce scan/shuffle (e.g., `completion_date` filter).
3. Disable auto-broadcast for big tables and **broadcast only small reference tables explicitly**.
4. Use **`.explain()`** before executing joins to understand shuffle behavior.
5. Use **Iceberg** or **Delta** for ACID-compliant bucketed & partitioned tables in Spark.
6. Avoid `.collect()` on large tables; use `.take(n)` or `.show(n)`.

---

💡 **Key takeaway**:

Bucketed tables + explicit filtering + controlled broadcast = **massive performance gain** for joins on large Spark tables, especially for fact × fact scenarios like `match_details × matches`.
